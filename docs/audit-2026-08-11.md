## CRITICAL

### C1. Hazard events are attributed to the tracker's `track_id`, not a real worker account — cross-wired to real accounts named the same way
**File:** `fieldpilot/events/bridge.py:54` (`hazard_to_event`)
```python
worker_id=f"w-{hazard.track_id}" if hazard.track_id is not None else None,
```
`track_id` comes from the BoT-SORT vision tracker (`fieldpilot/core/vision_engine.py:100`) — a per-session, per-camera counter assigned by order of appearance in frame, with no link to authentication or a phone's identity. Real worker accounts are seeded with exactly the same ID scheme: `auth/service.py:238-241` creates `w-1` (Ravi) and `w-2` (Anita), and `auth/service.py:98` documents `w-<n>` as the site-wide convention.

**Failure scenario:** A camera (the shared browser/server pipeline, or a worker's own rear-facing phone camera per `display/server.py:362-364`, which the code's own comment admits sees colleagues, not its owner) detects a person. The tracker assigns them, say, `track_id=2` because they're the second person to appear in that session. The bridge emits `Event(worker_id="w-2", ...)`. That event is then correctly (and IDOR-safely) scoped by `/me/alerts` (`backend/app.py:472-479`) to whoever authenticates as `w-2` — i.e., the real worker Anita, who may be nowhere near that camera, receives/hears a hazard alert about a stranger or a colleague. Any camera restart or new session resets the tracker's counter, so which real worker "absorbs" a given track number is essentially arbitrary and shifts run to run.

Compounding this: `display/server.py:623-635` runs **one shared Pipeline/tracker instance** for every phone and the anonymous browser page combined, so track IDs (and the misattribution) mix across unrelated cameras/workers, not just within one camera's session.

**What breaks:** `/me/alerts` scoping (an authenticated worker gets alerts that are not about them), which worker's device receives a spoken/pushed alert via `/ws?kind=device&worker_id=...` (`backend/app.py:1203-1213`, see C3), and any downstream safety-score/timeline aggregation keyed by `worker_id`.

**No mitigation found**: nothing checks that a track_id corresponds to a worker who is actually checked in nearby before attribution.

**Suggested fix:** Only attribute a hazard to a real worker_id when there is direct evidence of identity — e.g., the ingest `worker_id` query param the *transmitting phone* declared (already carried as `source_camera`/`source_zone` in the payload per the bridge's own comment) for own-camera hazards, and leave `worker_id=None` (zone/camera-scoped only, no per-worker attribution) for the shared/browser pipeline where no phone identity exists. Do not use tracker output as an identity.

### C2. Nearly the entire backend REST surface has no authentication
**File:** `fieldpilot/backend/app.py` (grep-verified: only `/auth/*`, `/me/*`, `/zones/{id}/enter|leave`, `/zones/occupancy`, `/questions*`, `/messages*` use `Depends(any_user|manager_only|worker_only)`)

Confirmed unauthenticated live (`curl`, no header, all return 200) and by absence of any `Depends(...)` in the handler signature:
- `/events`, `/events/stats` (~781-801)
- `/alerts`, `/alerts/stats`, `/alerts/{id}`, and the **mutating** `/alerts/{id}/resolve`, `/suppress`, `/unsuppress`, `/acknowledge`, `/alerts/{id}/feedback` (805-1103) — anyone can silence or dismiss a live safety alert with zero credentials.
- `/rules` GET/POST, `/rules/{id}` GET/PUT/DELETE (895-927) — anyone can rewrite what becomes an alert.
- `/notifications`, `/rfis*`, `/inspections*` (931-982)
- `/config`, `/config/tracked-items`, `/config/monitoring` (986-1016) — anyone can disable PPE/hardhat tracking or change confidence thresholds.
- `/models`, `/models/select`, `/learning/train`, `/learning/runs*` (1018-1162)
- `/zones` GET/POST, `/zones/{id}` GET/PUT/DELETE (1064-1099) — anyone can create/edit/delete site zones.
- `/blueprints*` (1166-1199)
- `@app.websocket("/ws")` (1203-1227) — see C3.
- `/broadcast/clients` (1229-1231)
- `/workers`, `/workers/{worker_id}/timeline` (1235-1274) — any worker's alert history/safety score readable by anyone, and this isn't even IDOR since there's no auth to bypass in the first place.
- `/control/inspection` GET/POST (1278-1291)

By contrast `/me/alerts` correctly returns `401` with no token (live-verified), proving the pattern for gating exists and is simply not applied to most of the surface.

**Failure scenario:** anyone on the network (or, given the wide-open CORS discussed in C2b, anyone who can reach the host at all — CORS does not protect non-browser clients) can `POST /alerts/{id}/resolve` to make a real, unaddressed hazard disappear from the dashboard, or `PUT /config` to turn off PPE detection entirely, with no login.

**Suggested fix:** add `Depends(manager_only)` to all mutating/administrative routes and `Depends(any_user)` to read-only ones, mirroring the already-correct `/me/*` pattern.

### C3. `/ws` websocket accepts an unauthenticated, client-declared `kind`/`worker_id`
**File:** `fieldpilot/backend/app.py:1203-1213`
```python
@app.websocket("/ws")
async def websocket_endpoint(ws, kind="dashboard", zone=None, worker_id=None):
    await ws.accept()
    client = await hub.connect(ws, kind=kind, zone=zone, worker_id=worker_id)
```
No token is checked before `ws.accept()`. `BroadcastHub` routes purely on these client-supplied query params (`fieldpilot/broadcast/hub.py`).

**Failure scenario:** connecting with `?kind=dashboard` receives every dashboard-audience publish site-wide, including other people's direct messages/voice notes and RFIs, with no login. Connecting with `?kind=device&worker_id=w-2` receives the alerts (including synthesized speech text) meant for worker `w-2`'s device — i.e., one worker's hazard alerts can be intercepted, or a manager-only broadcast stream can be silently tapped, by anyone who knows the query-string shape (which is documented in this very codebase).

**Suggested fix:** require a bearer token (or short-lived signed ticket minted by an authenticated REST call) before `ws.accept()`; derive `kind`/`worker_id` from the resolved identity, never the query string — same pattern as `_worker_id(user)` used correctly elsewhere.

### C4. Edge/display server (`:8000`) has no authentication anywhere, exposing live worker camera feeds and a roster of on-site workers
**File:** `fieldpilot/display/server.py` (grep-verified: no import of `fieldpilot.auth`, no `Depends`/`Authorization` handling anywhere in the module)

Live-verified:
```
GET :8000/workers/live        -> 200   (enumerates every streaming worker_id + zone + display name)
GET :8000/workers/{worker_id}/stream -> 200  (MJPEG feed with detection boxes, indefinite)
```
- `@app.websocket("/ws/video")` (`server.py:643-676`) accepts `worker_id`, `zone`, `name` as bare, unverified query params — anyone can inject frames claiming to be any worker's phone, or watch/scrape `/workers/{worker_id}/stream` for any worker with no session or role check.
- This is a live, unauthenticated video feed off a real person's phone/site camera, plus a live roster of who is currently on site — independent of whatever auth the backend on :8100 does or doesn't enforce.

**Suggested fix:** wire the same `AuthService`-backed dependency into `display/server.py`, gating `/workers/{worker_id}/stream` and `/workers/live` to authenticated managers, and validating the phone's claimed identity on `/ws/video` against a token instead of trusting the query string.

### C5. One shared vision-pipeline/tracker instance serves every phone and the browser page concurrently
**File:** `fieldpilot/display/server.py:508-519` (`browser_holder`), `:623-635` (`browser_pipeline()`), `:660` (`pipeline = await browser_pipeline()` called unconditionally for every connection regardless of `worker_id`)

The module's own comment (`server.py:511-514`) states the rationale for a *separate* instance per camera: "BoT-SORT track state, fall-velocity buffers and PPE cooldowns are per-camera — feeding two cameras through one set of detectors would cross their track IDs." But every phone/browser connection is routed through the same single `Pipeline`/`VisionEngine` (`vision_engine.py:69-78`, `model.track(..., persist=True, ...)`), which is exactly the scenario the comment warns against. `browser_gate = asyncio.Lock()` prevents a crash from concurrent calls, but does not stop frames from different real cameras being interleaved through one stateful tracker.

**Failure scenario:** with two workers' phones streaming simultaneously, BoT-SORT track IDs, fall-velocity history, and PPE/proximity cooldowns are cross-contaminated across unrelated cameras — worsening C1's misattribution (which camera's frame produced which track_id becomes even less well-defined) — and every connected phone's effective frame rate is globally serialized to one detector's throughput (adding a second worker roughly halves everyone's fps rather than scaling).

**Suggested fix:** either enforce true one-pipeline-per-camera (per the code's own stated design) or, if resource constraints require a shared model, keep per-camera tracker/cooldown state keyed by `worker_id`/`camera_id` instead of one global tracker.

### C6. Worker app's hazard-detection camera feed dies silently and never recovers on its own
**File:** `worker_app/lib/core/camera_stream.dart:184-197` (socket handlers), `:78` (`_streaming` flag), `:112` (`start()` guard)
```dart
onDone: () { _connected = false; notifyListeners(); },
onError: (Object e) { _connected = false; error = '...'; notifyListeners(); },
```
Confirmed by direct read: only `_connected` is reset; `_streaming` and `_channel` are left as-is. `start()`'s very first line, `if (_streaming || _starting) return;` (line 112), makes any later call to `start()` (including the automatic `_syncCamera` re-invocation on zone change, `main.dart:169-179`) a silent no-op once `_streaming` is stuck `true`. There is no reconnect/backoff logic anywhere in this file — contrast with the sibling socket in `worker_app/lib/core/live_feed.dart:197-215`, which has full exponential-backoff reconnect. Grep of the whole `worker_app/lib` tree for `CameraStream`/`reconnect` confirms `camera_stream.dart` is the only networked component without one.

**Traced impact precisely (refines, doesn't just repeat, the original theory):**
- The per-frame capture callback (`_onImage`, lines 234-274) is throttled by a timestamp gate to `targetFps` (10 Hz default) — most raw-sensor-rate callbacks exit cheaply before doing any real work, so it is *not* full-sensor-rate waste as initially suspected.
- At the throttled 10 Hz, the app still allocates and copies a full NV21 frame (~300-460 KB) and calls `channel.sink.add(payload)` on a channel whose remote end is gone. Tracing into the `web_socket_channel`/`web_socket` package source shows this throw is caught and swallowed *inside the package's own internal listener*, never reaching `camera_stream.dart`'s catch block — so it's a silent no-op, not a repeated exception storm or an unbounded backlog.
- The dominant real cost is that `controller.startImageStream` is never stopped, so **the camera hardware/ISP pipeline keeps running** for as long as `_streaming` stays true — a genuine, continuous battery draw (hundreds of mW class) for zero benefit, for the rest of the shift.
- Partial, accidental self-healing: `main.dart`'s app-lifecycle handler tears down and restarts the camera on any background/foreground transition (screen lock/unlock), so a phone that gets locked at all will recover by accident. A phone mounted with an always-on screen, or a worker who stays continuously in the app, will not recover until manual STOP/RESUME or an app restart.
- Misleading telemetry: `framesSent` keeps incrementing and the UI badge shows "Connecting…" (not an error state) during the outage (`camera_tab.dart`), giving a false impression that the feed is still attempting to reconnect and/or delivering frames.

**Suggested fix:** in `onDone`/`onError`, also set `_streaming = false` (and stop `controller.startImageStream`), and add the same exponential-backoff reconnect pattern already present in `live_feed.dart`.

## IMPORTANT

### I1. `events/bus.py` `InMemoryEventBus` never prunes its task list
**File:** `fieldpilot/events/bus.py:98` — every dispatched handler task is appended to `self._tasks` and never removed. Unbounded memory growth over a long-running process (one entry per event ever handled). **Confirmed.**

### I2. Hazard-path failures can be silently swallowed
**File:** `fieldpilot/backend/service.py:103` — if `events.save_event()` raises, the exception is caught by the bus's generic handler wrapper and the entire trigger→rules→notify chain for that event never runs, with no retry or dead-letter queue, and (per the subagent's trace) no loud alerting on the failure. **Plausible, not fully exercised** — I did not manufacture a failing `save_event()` call to observe behavior live; the code path was read but not executed.

### I3. Tracker's fallback ID is unstable across frames
**File:** `fieldpilot/core/vision_engine.py:100` — when the tracker drops an id, the fallback `track_id = -(i+1)` changes every frame. Since `Event.dedup_key()` incorporates `worker_id` (which derives from `track_id`, C1), this could defeat dedup and spam duplicate alerts for what is really one ongoing hazard, or, contrarily, generate a churn of distinct-looking events per frame. **Plausible, not fully confirmed against dedup_key's exact field list** — worth a direct look at `events/schema.py`'s `dedup_key()` before fixing.

### I4. `GET /alerts?worker_id=...` and `GET /workers/{id}/timeline` have no per-caller scoping even independent of the missing-auth issue
**File:** `fieldpilot/backend/app.py:805`, `:1235-1274` — contrast with `GET /me/alerts` (correctly derives `worker_id` from the token) and `GET /messages/{worker_id}` (`719-730`, explicit `if role=="worker" and _worker_id(user)!=worker_id: 403`). If C2 is fixed by only adding a generic `Depends(any_user)` without also adding worker-role scoping here, this reintroduces an IDOR even after "auth" is nominally added. **Confirmed as designed** (the missing check is real); flagging as a fix-adjacent trap, not a live exploit today only because there's no auth at all yet.

### I5. Demo credentials shipped enabled by default
**File:** `config.yaml:140` (`auth.seed_demo_users: true`), `fieldpilot/auth/service.py:276-296` — seeds `manager/manager123`, `worker1/worker123` (`w-1`), `worker2/worker123` (`w-2`) whenever the users table is empty. The code logs a warning but nothing prevents a real deployment from shipping with this default on. Given C2/C3/C4 make most of the platform reachable without any login at all, this specific finding is secondary right now, but becomes the live attack surface the moment auth gating is added back without also disabling this default. **Confirmed** (config + seeding code both read directly).

### I6. Second/overlapping connection for the same worker can be torn down by the wrong `finally`
**File:** `fieldpilot/display/feeds.py:81-93` (`open`), `:117-119` (`close`, unconditional `self._feeds.pop(worker_id, None)`) — no reference counting. If the same `worker_id` briefly has two concurrent `/ws/video` connections (app reconnect racing old socket teardown — made more likely by C6's total absence of reconnect logic, or trivially by two clients claiming the same id per C4), whichever connection's cleanup runs first deletes the shared feed entry out from under the other, still-live connection, which then silently no-ops on every subsequent `publish()` (`feeds.py:101-103`). **Confirmed by code read**; not observed live under an actual race.

### I7. Primary server-camera pipeline task can die with zero log output, ever
**File:** `fieldpilot/display/server.py:578`, shutdown at `:585-589`:
```python
task.cancel()
try:
    await task
except (asyncio.CancelledError, Exception):  # noqa: BLE001
    pass
```
`pipeline.py`'s `run()` loop has no per-iteration try/except around frame processing; any unhandled exception propagates out of the task with nothing to log it during normal operation, and is swallowed by the bare `pass` at shutdown. The only visible symptom is the `/stream` endpoint going stale. By contrast, the phone/browser ingest path (`server.py:695-705`) correctly wraps each frame and logs+continues — that path is fine. **Confirmed by code read.**

### I8. Two of four per-track safety-detector cooldown dicts leak unboundedly
**File:** `fieldpilot/safety/ppe.py:312` (`self._last_alert`) and `fieldpilot/safety/proximity.py:34` (`self._last`) — written per-alert, never pruned (grep-confirmed no `.pop`/`del` anywhere in either file). Contrast: `fall.py:138-143` and `attention.py:145-146` both correctly forget stale tracks. Since track IDs churn constantly (worsened by C5's shared-tracker issue), these two dicts grow for the life of the process. **Confirmed by code read**, slow-burn severity (a memory leak, not a crash-now bug).

## MINOR

- **M1.** `frontend/src/components/NavBadges.tsx:47` — sidebar alert-count badge queries only `state: "ACTIVE"`, undercounting `NEW` alerts relative to what the rest of the dashboard treats as "outstanding." Confirmed by reading both the badge query and the alerts page's state handling.
- **M2.** `frontend/src/app/login/page.tsx:96` — demo manager credentials are printed directly on the sign-in screen. Low-severity in isolation, but combined with C2 (most routes unauthenticated anyway) it's a moot point today and a real problem the moment auth is actually enforced, if this is left in for a production build.
- **M3.** Dead backend endpoints with no caller found in either `frontend/` or `worker_app/`: `POST /rules`, `GET/DELETE /rules/{id}`, `GET /alerts/stats`, `GET /alerts/{id}`, `POST /alerts/{id}/acknowledge`, and the entire `/config`, `/models`, `/learning/*`, `/blueprints/*`, `/broadcast/clients` surface. Also unauthenticated (see C2) — dead code that is simultaneously exposed attack surface.
- **M4.** Stale copy: `frontend/src/app/rules/page.tsx:46` states rules are "stored in PostgreSQL," but `config.yaml:144` sets `backend: sqlite` as shipped. Cosmetic, but literally false about the running system.
- **M5.** `frontend/src/lib/useLiveFeed.ts:76` derives the live-feed WS URL from `window.location.hostname:8100`, bypassing the Next.js proxy/rewrite (websockets aren't proxied that way). Works today because frontend and backend happen to share a hostname in this deployment; there is a `NEXT_PUBLIC_FIELDPILOT_WS` override, but it's easy to forget on a different topology. Degrades to polling rather than hard-failing, so genuinely minor.

- **M7.** `worker_app` telemetry: the "Sent" frame counter (`camera_tab.dart:210`, driven by `camera_stream.dart:256`) keeps incrementing during a C6 outage, and the "Connecting…" badge label implies an active retry that isn't happening. Misleading, not damaging.
- **M8.** `worker_app/lib/screens/messages_tab.dart:80-90` vs `176-213` — if the widget is disposed while a voice-note hold-to-record is in progress, the native recorder is safely stopped/released by the `record` plugin's own `dispose()` (traced through `record_android`'s native code — mic is not leaked), but the temporary `.m4a` file created for that recording is never deleted, leaving orphaned files in the OS temp directory over time. Disk litter, not a resource/mic leak.

## What was checked and found FINE (useful negative information)

**Auth service internals** (`fieldpilot/auth/service.py`): scrypt password hashing with per-record upgradeable cost params, opaque 256-bit session tokens (SHA-256 hashed at rest, no JWT so no signature-bypass class of bug), timing-equalized login (dummy derivation on unknown username), session revocation on password change/deactivation, expiry+revocation both checked in `resolve_token`. Well designed — the problem is that most routes simply don't call it (C2), not that the service itself is weak.

**Routes that ARE correctly gated and scoped** (backend/app.py): `/auth/login`, `/auth/logout`, `/auth/me`, `/auth/users` (manager_only); `/me/alerts` GET/POST, `/me/zone`, `/zones/{id}/enter|leave`, `/me/messages` — all `worker_only` with `worker_id` derived from the token, never trusted from client input (correct, IDOR-safe in isolation); `/questions*` and `/messages*` — explicit ownership checks (`if role=="worker" and worker_id mismatch: 403`) present and correct.

**Upload path traversal**: `_save_upload` (`app.py:403-425`) never trusts client filenames for storage paths (server-generated UUID + allowlist extension); `resolve_image_path`/`resolve_audio_path` (`workforce/questions.py`, `workforce/messages.py`) both reject anything outside an allowed root via `is_relative_to`. No traversal found.

**CORS**: restricted to `localhost:3000`/`127.0.0.1:3000`, no `allow_credentials=True` — not independently exploitable, though moot given non-browser clients bypass CORS entirely (as this audit's own curl checks did).

**Event bus architecture rule** ("model must publish an event, never call notification/dashboard directly"): grepped `fieldpilot/safety/`, `fieldpilot/inspection/`, `fieldpilot/core/` — no model code found calling notification/broadcast APIs directly. The bus-vs-direct-dispatcher branch in `core/pipeline.py`/`display/server.py` is a legitimate conditional, not an architecture violation.

**Rules/trigger engine dedup and cooldown logic** (`rules/engine.py:225-238`, `triggers/engine.py:128-186`): correctly designed for the normal (non-C1/C3-poisoned) case.

**RedisEventBus** dedup of duplicate pmessage deliveries (`events/bus.py:161-189`): correct.

**Video ingest resource handling on the happy path**: `LatestFrame` mailbox, `VideoSource`'s bounded `queue.Queue` with drop-oldest and guaranteed `cap.release()`, `LiveState`'s bounded deque, `FeedRegistry`'s locking, and the `ws_video` `finally` block's cleanup ordering were all read and are correct — the leaks found (I6, I8) are narrower than a wholesale resource-management problem.

**MJPEG stream generators**: both `/stream` and `/workers/{id}/stream` sleep every iteration (no busy-loop) and the per-worker one has an explicit 30s idle timeout.

**Voice-note recorder**: traced through the `record`/`record_android` plugin's native `dispose()` — the microphone is always released even if the widget is torn down mid-recording. Only the leftover temp file (M8) is a real, minor issue.

**Worker app ↔ backend contract**: every endpoint, HTTP method, and field name in `worker_app/lib/core/api_client.dart` was diffed against `fieldpilot/backend/app.py`'s actual routes (auth, `/me/*`, zones, questions, messages) and the `/ws/video` raw-frame header format against `fieldpilot/display/server.py` — all matched, no drift found. Other unbounded-growth candidates checked and found capped: `LiveFeed._frames` (max 40), `Voice._spoken` (max 300, oldest evicted).

**Frontend ↔ backend contract**: broad field/path/method match confirmed for `/auth/*`, `/alerts` (+ resolve/suppress/unsuppress), `/workers`, `/rules` (GET/PUT), `/notifications`, `/zones` CRUD + occupancy, `/questions*`, `/rfis*`, `/inspections*`, `/control/inspection`, `/messages/*`, and the edge's `/workers/live` + `/workers/{id}/stream`.

## Most important finding, restated

C1 + C3 + C2 together form the real headline: a detected person's hazard is attributed to a worker account using nothing more than a vision tracker's transient, resettable counter, and there is no authentication anywhere on the path (backend REST, backend `/ws`, or the edge server) that would stop that misattributed — or entirely fabricated — alert from being read, resolved, suppressed, or spoken aloud on someone else's phone. Fixing only the auth gaps without also fixing the worker_id derivation in `hazard_to_event()` would leave a fully authenticated system that still pages the wrong worker for a hazard that has nothing to do with them.
